§1Overview

A shell is an ordinary user program that reads commands and asks the operating system to run them. It isn't part of the kernel. Every action it takes, like starting a program, connecting two programs, or stopping one, goes through a system call. That makes a shell one of the best programs for showing how an OS manages processes.

MiniShell++ is our own Unix shell, written in C++. It works like a small Bash. For DA-2 we promised to complete 80% of the execution, and the following already works:

  • Running any program installed on the system (ls, grep, python3 and so on)
  • Parsing command lines with quotes, escapes, variables ($HOME, $?) and ~
  • Pipes, which connect programs: cat file | sort | uniq
  • I/O redirection: <, >, >>, 2>, 2>&1
  • Background jobs with &
  • Full job control: Ctrl-Z, Ctrl-C, jobs, fg, bg, kill
  • Signal handling, so the shell itself survives Ctrl-C and Ctrl-Z
  • 14 built-in commands, command history, and !! / !N re-execution
Summary for the presentation

"MiniShell++ reads a line, parses it into a pipeline of commands, and creates one process per command using fork() and execvp(). It connects the processes with pipe() and dup2(), puts them in their own process group, gives that group the terminal, and waits for them with waitpid(). Signals handle Ctrl-C and Ctrl-Z, and a job table tracks background and stopped jobs."

§2Build & run

You need macOS or Linux, a C++17 compiler (g++ or clang++) and make.

# 1. go to the project folder
cd ~/Documents/OS-Da

# 2. compile (creates the ./minishell executable)
make

# 3. start the shell
./minishell

# run the automated tests
make test

# other ways to run it
./minishell -c "ls | wc -l"      # run one command and exit
./minishell myscript.msh         # run commands from a file

The Makefile compiles each src/*.cpp file into build/*.o, then links the object files into minishell. It uses -Wall -Wextra -Wpedantic, and the build currently produces zero warnings. make clean deletes all build output.

What happens when you press Enter

Every command line goes through the same stages. Each stage is handled by one module:

The core data structures

The parser turns text into these structs, and the executor only reads them. Keeping the two stages separate like this is a standard compiler-style design.

include/parser.h
struct Redirect {
    enum class Kind { Read, Write, Append, Duplicate };
    Kind kind;
    int fd;              // which descriptor: 0 stdin, 1 stdout, 2 stderr
    std::string target;  // file name
    int sourceFd;        // for 2>&1 → fd=2, sourceFd=1
};
struct Command  { std::vector<std::string> argv; std::vector<Redirect> redirects; };
struct Pipeline { std::vector<Command> commands; bool background; std::string text; };

For example, grep -i err < log.txt | sort > out.txt & becomes:

Pipeline {
  background: true,  text: "grep -i err < log.txt | sort > out.txt"
  commands: [
    Command { argv: ["grep","-i","err"], redirects: [ {Read, fd 0, "log.txt"} ] },
    Command { argv: ["sort"],            redirects: [ {Write, fd 1, "out.txt"} ] }
  ]
}

struct Process { pid_t pid; bool completed, stopped; int status; };
struct Job {
    int id;                      // the [1], [2] number users see
    pid_t pgid;                  // process group of the whole pipeline
    std::string command;
    std::vector<Process> procs;  // one per command in the pipeline

§4Code walkthrough, file by file

main.cpp: the read-eval loop

The program starts here. It works out whether it is running interactively, sets the shell up, and then loops forever:

bool interactive = inputFd == STDIN_FILENO && isatty(STDIN_FILENO);
initShell(interactive);

while (g_shell.running) {
    if (g_childChanged) { g_childChanged = 0; g_shell.jobs.reap(); }  // SIGCHLD arrived
    g_shell.jobs.notify(interactive);        // "[1]+ Done  sleep 5"
    if (interactive) std::cout << buildPrompt();
    int r = readLine(inputFd, line);
    if (r == 0)  break;                      // Ctrl-D (EOF)
    if (r < 0)  { std::cout << '\n'; continue; }  // Ctrl-C at prompt
    runLine(line);
}
  • isatty() checks whether stdin is a real terminal. Job control is only enabled if it is. When the shell reads from a file or pipe (like the tests do), there is no terminal to hand over.
  • The program accepts three modes: no arguments (interactive), -c "command", or a script file name.
  • If you press Ctrl-D while jobs are stopped, the shell warns "There are stopped jobs." once, the same way Bash does.

shell.cpp: setup, prompt, input, history

initShell(): taking control of the terminal

// wait until we are in the foreground
while (tcgetpgrp(terminalFd) != (pgrp = getpgrp()))
    kill(-pgrp, SIGTTIN);
installShellSignals(interactive);
setpgid(0, 0);                          // shell gets its own process group
g_shell.pgid = getpgrp();
tcsetpgrp(terminalFd, g_shell.pgid);    // that group now owns the terminal
tcgetattr(terminalFd, &g_shell.tmodes); // remember terminal settings

This is the standard startup sequence for a job-control shell, as described in the GNU C Library manual. Only one process group can own a terminal at a time. The shell makes sure it owns the terminal before it starts.

readLine(): input with the read() system call

We read input with the raw read() system call instead of std::getline, because we need to detect Ctrl-C. When SIGINT arrives, read() fails with errno == EINTR. We check the flag our handler set, return -1, and the main loop prints a fresh prompt. If a SIGCHLD interrupts the read instead, we just keep reading.

buildPrompt()

This function builds minishell++ [130] user@host:~/dir$ using getenv("USER"), gethostname() and getcwd(). The home directory is shortened to ~, and ANSI escape codes add the colours. The red [130] only appears when the last command failed.

expandHistory() and runLine()

Before parsing, !! is replaced with the previous command, !5 with command number 5, and !-2 with the command two back. Anything inside single quotes is left alone. The expanded line is printed so the user can see what will run. runLine() then saves the line to history, parses it, and runs it with executePipeline(). If parsing fails, $? is set to 2, as in Bash.

parser.cpp: turning text into structure

Parsing has two stages.

Stage 1: tokenize()

This scans the line one character at a time and produces tokens: words and operators (|, &, <, >, >>, N>&M). It is a small hand-written state machine:

InputRuleExample → result
space / tabends the current wordls -l → ls, -l
'...'everything literal, no expansion'$HOME' → $HOME
"..."spaces kept; $VAR expanded; \" \\ \$ escapes"hi $USER" → hi navaneeth
\xnext character taken literallya\ b → one word a b
$VAR ${VAR}replaced with getenv(); unset variables disappear${HOME}/x

~at the start of a word → $HOME~/Documents
#at the start of a word → rest of line ignoredls # comment

An inWord flag lets "" (an empty quoted string) count as a real argument, while $UNSET_VAR produces no argument at all. Bash behaves the same way.

Stage 2: parseLine()

This walks the tokens and builds the Pipeline:

  • A Word is added to the current command's argv.
  • | finishes the current command and starts a new one. If the current command is empty, that's a syntax error (| ls).
  • < > >> must be followed by a word, which becomes the file name. Otherwise the error is syntax error near unexpected token `newline'.
  • & must be the last token. It sets background = true.

Errors are raised as a ParseError exception inside the parser, caught in one place, and returned as a message. The executor therefore never sees a half-built pipeline.

executor.cpp: where processes are created

This is the most important file for the OS course.

Decision: run in the shell or fork?

if (pl.commands.size() == 1 && !pl.background && isBuiltin(argv[0]))
    return runBuiltinInShell(pl.commands[0]);

A built-in like cd has to run inside the shell process. If it ran in a child process, the child's working directory would change and then the child would exit, leaving the shell where it was. Built-ins that are part of a pipeline, such as echo hi | tr a-z A-Z, run in a child process, as they do in Bash.

runBuiltinInShell() still supports redirection (echo hi > f.txt). It backs up each affected fd with fcntl(fd, F_DUPFD_CLOEXEC, 10), applies the redirects, runs the built-in, and then uses dup2 to put the original fds back.

The pipeline loop

src/executor.cpp · executePipeline()
int inFd = STDIN_FILENO;               // where the next command reads from
for (size_t i = 0; i < n; ++i) {
    int pipefd[2] = {-1, -1};
    if (i + 1 < n) pipe(pipefd);          // not needed after the last command

    pid_t pid = fork();
    if (pid == 0) {                      // ───── CHILD ─────
        setpgid(0, pgid == 0 ? 0 : pgid);  // join the job's process group
        if (!background) tcsetpgrp(tty, getpgrp());
        resetChildSignals();               // Ctrl-C/Z should affect me normally
        if (inFd != 0) { dup2(inFd, 0); close(inFd); }
        if (pipefd[1] >= 0) { dup2(pipefd[1], 1); close(pipefd[1]); close(pipefd[0]); }
        runChild(cmd);                     // redirects, then execvp — never returns
    }
    // ───── PARENT (shell) ─────
    if (pgid == 0) pgid = pid;              // first child's PID becomes the group ID
    setpgid(pid, pgid);                    // done in both processes to avoid a race
    if (inFd != 0) close(inFd);            // shell must close its copies of pipe ends
    if (pipefd[1] >= 0) { close(pipefd[1]); inFd = pipefd[0]; }
}

runChild(): redirection and exec

if (!applyRedirections(cmd.redirects)) _exit(1);
if (isBuiltin(argv[0])) _exit(runBuiltin(argv));   // built-in inside a pipeline
execvp(args[0], args.data());                       // replaces this process image
// only reached if exec failed:
if (errno == ENOENT) { cerr << "command not found"; _exit(127); }
_exit(126);                                         // e.g. permission denied

applyRedirections() goes through the redirects in order. For > file it runs open(file, O_WRONLY|O_CREAT|O_TRUNC, 0644), then dup2(fd, 1), then close(fd). >> uses O_APPEND instead of O_TRUNC, and 2>&1 is simply dup2(1, 2). Because the order is kept, cmd > f 2>&1 sends both streams to the file, while cmd 2>&1 > f does not. That matches Bash.

The child calls _exit() rather than exit() so that it doesn't flush stdio buffers it copied from the parent. Flushing them would print the same output twice.

waitForeground(): waiting and job control

tcsetpgrp(tty, job.pgid);                    // give terminal to the job
if (resume) { job.markRunning(); kill(-job.pgid, SIGCONT); }   // used by fg

while (job.state() == JobState::Running) {
    pid_t pid = waitpid(-1, &status, WUNTRACED); // also returns when a child STOPS
    g_shell.jobs.updateStatus(pid, status);
}
tcsetpgrp(tty, g_shell.pgid);                 // take the terminal back
tcgetattr(tty, &job.tmodes);                  // save job's terminal modes (e.g. vim)
tcsetattr(tty, TCSADRAIN, &g_shell.tmodes);   // restore shell's

if (job.state() == JobState::Stopped) print("[1]+  Stopped  sleep 30");
else { report signal if killed; jobs.remove(job.id); }

The WUNTRACED flag is what makes Ctrl-Z work. Without it, waitpid would ignore a stopped child and the shell would hang. The exit status follows the shell convention: normal exit gives code, death by a signal gives 128 + signal number. So Ctrl-C (SIGINT = 2) gives $? = 130, and Ctrl-Z (SIGTSTP = 18 on macOS) gives 146. On Linux SIGTSTP is 20, so you get 148.

jobs.cpp: the job table

JobTable keeps a std::map<int, Job> ordered by job ID. Pointers to elements of a std::map stay valid when other jobs are added or removed, which matters because fg holds a Job& while other jobs finish.

signals.cpp: surviving Ctrl-C and Ctrl-Z

void installShellSignals(bool interactive) {
    setHandler(SIGCHLD, onSigchld, SA_RESTART);  // only sets a flag
    if (!interactive) return;
    setHandler(SIGINT,  onSigint, 0);            // no SA_RESTART → read() is interrupted
    setHandler(SIGQUIT, SIG_IGN, 0);
    setHandler(SIGTSTP, SIG_IGN, 0);             // Ctrl-Z must not stop the shell
    setHandler(SIGTTIN, SIG_IGN, 0);
    setHandler(SIGTTOU, SIG_IGN, 0);             // needed to call tcsetpgrp() from background
}
void resetChildSignals() { /* SIG_DFL for all of the above + empty signal mask */ }
Design decision: async-signal safety

A signal handler can run in the middle of any instruction, including while a std::map is being modified. Calling printf, malloc or container methods inside a handler is undefined behaviour. So our handlers only write a volatile sig_atomic_t flag, and the main loop does the real work of reaping and printing when it is safe to. This is the textbook "self-flag" pattern.

The child resets its signal dispositions itself because ignored signals (SIG_IGN) stay ignored after exec. Only signals with handlers are reset automatically. Without this step, Ctrl-C wouldn't work on programs started from our shell.

§5OS concepts demonstrated

1. Process creation: fork() and exec()

Unix creates processes in two steps.

fork()

Duplicates the calling process. The child gets a copy of the parent's memory (copy-on-write), its open file descriptors, environment and working directory. It returns twice: 0 in the child and the child's PID in the parent.

execvp()

Replaces the current program with a new one, searching $PATH for it. The PID and open file descriptors stay the same. If it succeeds it never returns.

Why two steps? The gap between fork and exec is where the child can set itself up. It redirects fds, joins a process group and resets signals, all without the new program knowing. That gap is how the shell implements pipes and redirection.

2. Process termination, exit status and zombies

When a process exits, the kernel keeps a small record of it (PID and exit status) until the parent collects it with waitpid(). A process in that state is a zombie. If a shell never collects its children, zombies pile up and fill the process table. MiniShell++ collects every child: foreground jobs in waitForeground(), background jobs in reap() after each SIGCHLD.

3. File descriptors and I/O redirection

Each process has a file descriptor table, which maps small integers to open files, pipes or terminals. By convention 0 is stdin, 1 is stdout and 2 is stderr. Programs like ls just write to fd 1 without knowing what it points to.

Redirection means changing what an fd points to before calling exec. dup2(old, new) makes new refer to the same open file as old, closing whatever new pointed to before.

// sort < in.txt >> out.txt 2>&1   — what the child does before exec:
fd = open("in.txt", O_RDONLY);                      dup2(fd, 0); close(fd);
fd = open("out.txt", O_WRONLY|O_CREAT|O_APPEND, 0644); dup2(fd, 1); close(fd);
dup2(1, 2);
execvp("sort", ...);

4. Inter-process communication: pipes

pipe(fds) creates a one-way kernel buffer. fds[1] is the write end and fds[0] is the read end. Pipes are inherited through fork, so related processes can talk through them.

  • Blocking: a reader blocks while the pipe is empty, and a writer blocks while it is full (about 64 KB). The processes in a pipeline therefore run concurrently and pace each other automatically.
  • EOF: a reader only gets EOF once every write end is closed. That is why both the shell and each child close the pipe ends they don't use. Forgetting to do this is the most common pipeline bug, because wc hangs forever.
  • SIGPIPE: writing to a pipe with no readers raises SIGPIPE. In yes | head -1, yes is killed this way once head exits. Our shell doesn't print a message for SIGPIPE deaths, because they are normal.

5. Process groups, sessions and the controlling terminal

This is the concept that makes job control possible.

  • A process group is a set of processes identified by a PGID. All processes in one pipeline share a group, so one signal can reach the whole job: kill(-pgid, sig).
  • A session holds process groups and has at most one controlling terminal.
  • Exactly one group in the session is the foreground process group, set with tcsetpgrp(). When you press Ctrl-C, the terminal driver sends SIGINT to every process in the foreground group, and Ctrl-Z sends SIGTSTP the same way.
  • If a background process tries to read from the terminal, it receives SIGTTIN and stops.

The shell's job is to keep moving the foreground: to the job while it runs, and back to itself afterwards. That's why Ctrl-C kills sleep and not the shell. While sleep runs, the shell isn't in the foreground group at all.

6. Signals

Signals are software interrupts the kernel delivers to a process asynchronously. A process can accept the default action, ignore the signal, or catch it with a handler (sigaction).

8. Environment and inheritance

Environment variables, working directory, open fds and signal dispositions are all copied into a child at fork time. A child can never change its parent's copies. That is why cd and export are built-ins, and why export FOO=1 followed by env | grep FOO works: env inherits the environment of the shell that forked it.

Known limitations (be honest if asked)

  • Unquoted variables aren't word-split: $X containing spaces stays a single argument.
  • Only single-digit fd numbers work in redirects (2>, not 12>).

  • History is only kept in memory and is lost on exit (planned).

§9Presentation demo script

Run these in order. Each step shows one concept, so say the concept out loud as you type.

  1. Build it: make clean && make (run in your normal terminal). "Builds with zero warnings."
  2. Start it and show help: ./minishell, then help
  3. fork + exec: ls -l, then echo $$, then ps -o pid,ppid,pgid,comm. "ps is our child: its PPID is our PID, and it has its own PGID."
  4. Exit status: ls /nope, then echo $? (prompt shows [1]), then nosuchcmd (127)

§10Likely viva questions

Why does a shell use fork() and then exec(), instead of one call?

The gap between the two calls lets the child set up its environment before the new program starts. It redirects fds with dup2, joins a process group, and resets signals. The program being run needs no special code for any of this. posix_spawn combines both steps but is less flexible.

Why is cd a built-in? What happens if you run /usr/bin/cd?

The working directory is an attribute of each process. A child that calls chdir() changes only its own directory and then exits, so the shell's directory stays the same. For the same reason, export and exit also have to run inside the shell process.

What is a zombie process and how does your shell avoid them?

A zombie is a process that has exited but whose parent hasn't collected its status with wait. The kernel keeps its process table entry until then. Our shell collects foreground jobs in waitForeground(). For background jobs, the SIGCHLD handler sets a flag and the main loop calls reap(), which loops waitpid(-1, WNOHANG) until nothing is left.

What would happen if the parent didn't close the write end of the pipe?

The reading process (say wc) only sees EOF once every write end is closed. If the shell kept a copy open, wc would block forever and the pipeline would hang.

How does Ctrl-C kill the running program but not the shell?

The terminal driver sends SIGINT to the foreground process group. Before waiting, the shell makes the job's group the foreground group with tcsetpgrp(). The shell is in a different group, so it doesn't receive the signal. The shell also catches SIGINT for when you press Ctrl-C at the prompt.

How do fg and bg work internally?

bg sends SIGCONT to the job's whole group (kill(-pgid, SIGCONT)) and marks it as running in the background. fg does the same, but first gives the terminal to the job with tcsetpgrp, restores its saved terminal modes, and then waits for it with waitpid(..., WUNTRACED) like any other foreground job.

Why does setpgid() get called in both the parent and the child?

To avoid a race condition. After fork, either process might run first. If only the parent called it, the child could exec and read the terminal before joining its group. If only the child called it, the parent could try to hand the terminal to a group that doesn't exist yet. Calling it on both sides guarantees the group exists whichever process runs first.

Why does your signal handler only set a flag?

Handlers run asynchronously and can interrupt code that is halfway through changing the job table or an I/O buffer. Only async-signal-safe operations are allowed inside a handler, and writing a volatile sig_atomic_t is one of them. The real work happens later in normal code.

What does exit status 130 or 146 mean?

If a process was ended by a signal, the shell reports 128 + the signal number. SIGINT is 2, so 130 means Ctrl-C. SIGTSTP is 18, so 146 means the job was stopped with Ctrl-Z. 127 means the command wasn't found, and 126 means it was found but couldn't be executed.

What's the difference between > and >>, and how is 2>&1 done?

> opens the file with O_TRUNC, which empties it. >> uses O_APPEND, so every write goes to the end. 2>&1 is dup2(1, 2): fd 2 now points wherever fd 1 currently points. Redirects are applied left to right, which is why their order matters.

Which OS scheduling concepts does this show?

Processes in a pipeline run concurrently, and the kernel scheduler switches between them. Pipes also cause blocking and waking: a reader sleeps on an empty pipe and wakes when data arrives. Job control shows state changes between running, stopped (not schedulable) and terminated. wait is the shell blocking on the event of a child changing state.

Why use _exit() in the child instead of exit()?

exit() runs cleanup handlers and flushes stdio buffers. The child inherited a copy of the parent's buffers, so flushing them could print the parent's pending output a second time. _exit() ends the process immediately.
